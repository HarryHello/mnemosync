本文把对 Hermes Agent、Pi Agent、ChatLuna（长期记忆、角色卡、伪装群友、Character Card、辅助 Agent）的源码研究，整合为 Mnemosync 未来的统一人格架构设计，不代表当前版本承诺。

**只回答**：

1. 一个服务器权威人格从"定义"到"社交行动"需要哪些层
2. 角色卡导入、Lorebook、长期记忆、社交状态、辅助 Agent 如何构成统一系统
3. Mnemosync 核心与平台适配器各自的职责边界

## 3. Layer 1: Persona Definition — 人格定义层

### 3.1 核心洞察

角色卡（SillyTavern Character Card）和伪装群友（ChatLuna Character）的研究表明：

> "角色人格"与"群聊社会行为策略"不应该是同一个对象。

同一个人格在不同空间应有不同的社交行为，但核心身份不变。

### 3.2 建议的人格定义结构

```text
PersonaDefinition
├── identity
│   ├── name                名称
│   ├── description         身份、背景、外观
│   ├── personality         稳定性格描述
│   ├── values              核心价值观
│   └── speaking_style      语言风格
├── scenario
│   ├── default_scenario    默认场景
│   └── space_overrides     按空间覆盖的场景
├── examples
│   ├── dialogues           示例对话（Few-shot）
│   └── opening_messages    开场白
├── lorebook
│   └── entries[]           条件触发的静态知识
├── capabilities
│   ├── public              可公开的能力
│   └── internal            仅内部使用的能力
├── behavioral_limits
│   ├── never_do            永不执行的行为
│   ├── privacy_rules       隐私规则
│   └── role_boundaries     角色边界
├── social_policies
│   └── per_space[]         按空间类型的行为策略
└── metadata
    ├── version              语义化版本
    ├── author               作者
    ├── source               来源（角色卡 URL / 手动创建）
    ├── created_at
    └── updated_at
```

```text
└───────────┬─────────────┘
            │

┌─────────────────────────┐
│  Persona Draft            │
│  • 预览转换结果           │
│  • 人工确认/编辑          │
│  • 标记来源和版本         │
└───────────┬─────────────┘
            │

┌─────────────────────────┐
│  Authoritative Persona    │
│  • 服务器权威版本         │
│  • 不可被客户端覆盖       │
│  • 变更审计日志           │
└─────────────────────────┘
```

### 3.4 导入安全规则

- 限制文件大小、像素数量、tEXt 块大小
- 限制 JSON 深度和字符串长度
- 限制 Lorebook 条目数量
- `regex_scripts` 等可执行字段只能保留为不可执行元数据或直接丢弃
- Jailbreak Prompt 属于客户端角色扮演生态，不导入
- `system_prompt` 字段不可直接成为服务器权威指令，需经人工审核

### 3.5 Lorebook 与长期记忆的边界

| 维度     | Lorebook                   | 长期记忆                  |
| -------- | -------------------------- | ------------------------- |
| 来源     | 作者预定义                 | 对话中提取                |
| 内容     | 世界观、设定、角色关系     | 用户事实、偏好、事件      |
| 触发方式 | 关键词匹配                 | 语义检索 + 图检索         |
| 更新方式 | 作者手动更新               | Agent 自动提取 + 人工纠正 |
| 生命周期 | 随人格版本                 | 衰减、遗忘、纠正          |
| 典型案例 | "阿斯特拉是北方王国的首都" | "用户 A 喜欢 Rust"        |

两者可以共享相同的检索基础设施（向量库、图索引），但应保持独立的作用域和生命周期。

### 3.6 Social Policy — 按空间的行为策略

Social Policy 是人格对不同空间类型的**表达倾向**，通过 Prompt 引导实现，不依赖平台适配器做特殊处理。

```text
SocialPolicy(space_type)
├── participation
│   ├── verbosity             回复详细程度 (brief / normal / detailed)
│   ├── initiation            主动程度 (responsive_only / moderate / proactive)
│   └── formality             正式程度 (casual / normal / formal)
├── expression
│   ├── emoji_style           表情风格偏好 (frequent / occasional / never)
│   ├── quote_style           引用风格 (natural / minimal)
│   └── length_preference     篇幅偏好 (short / medium / long)
├── boundaries
│   ├── mute_topics[]         回避的话题
│   └── require_context       需要多少上下文才充分回应
└── silence
    └── passive_silence_enabled  是否启用可选被动沉默（超时/空响应）
```

示例：

```text
好友小群: 活跃、casual、偶尔表情、natural 引用
工作群: responsive_only、normal 正式度、minimal 表情
公共大群: responsive_only、极简回应
私聊: 允许 proactive、casual、可分段
```

**关键约束**：Social Policy 通过 Prompt 自然引导模型行为，不要求平台适配器识别任何自定义格式或协议。

## 4. Layer 2: Memory & Relationship — 记忆与关系层

### 4.1 核心洞察

ChatLuna 长期记忆插件最重要的设计是：

> **作用域（谁共享这批记忆）与检索引擎（如何存储和检索）是两个正交维度。**

同时，ChatLuna 的四层（Global/Preset/Guild/User）解决了共享范围，但没有解决主体和受众，因此不能直接作为隐私模型。

### 4.2 作用域 × 引擎的正交设计

```text
作用域（Scope）              检索引擎（Engine）
─────────────────────       ─────────────────────
Persona Core                 Basic（全量注入）
Actor Private                Embedding + Reranker
Space Public                 HippoRAG-like（向量 + 图）
Actor-in-Space Shared        EMGAS-like（激活扩散）
Persona Internal Experience  Hybrid
```

每个作用域可以独立选择引擎。例如：

- 人格核心记忆（少量）→ Basic 全量注入
- 用户私有记忆（中量）→ Embedding + Reranker
- 群公共记忆（大量）→ 向量 + 图混合检索

### 4.3 主体与受众分离

```text
MemoryEntry
├── content              记忆内容
├── subject_type         主体类型 (persona / actor / space / topic)
├── subject_id           主体标识
├── audience_type        受众类型
├── audience_id          受众标识
├── visibility           可见性
│   ├── persona_internal 仅人格内部
│   ├── actor_private    仅该参与者
│   ├── space_shared     指定空间内
│   └── persona_public   人格公开
├── provenance
│   ├── source_event_ids  来源事件
│   ├── extraction_model  提取模型
│   ├── prompt_version    提示词版本
│   └── confidence        置信度
├── lifecycle
│   ├── importance        重要性
│   ├── decay_rate        衰减率
│   ├── access_count      访问次数
│   ├── last_accessed     最后访问
│   ├── expires_at        过期时间
│   └── is_forgotten      是否已遗忘
├── conflicts
│   ├── supersedes        替代哪些记忆
│   └── superseded_by     被哪些记忆替代
└── metadata
    ├── created_at
    ├── updated_at
    └── version
```

### 4.4 检索时的受众过滤

```text
对群聊输出，默认可检索：
✅ 人格核心中允许公开的部分
✅ 当前群的空间公共记忆
✅ 当前用户明确允许在该群共享的记忆
✅ 当前群最近的可见事件和检查点
✅ 关系状态导出的行为提示（称呼、语气）

默认不可检索：
❌ 其他用户的私有记忆
❌ 当前用户只允许私聊使用的记忆
❌ 其他群的空间记忆
❌ 未经策略批准的跨群推断
❌ 仅凭模型判断"可能有用"但受众不匹配的内容
```

这是群聊架构文档中隐私不变量的核心：

> 先按受众过滤，再把记忆交给模型；不能先注入私密记忆，再仅靠提示词要求模型不要泄露。

### 4.5 记忆冲突与纠正

当用户说"我刚才开玩笑，我住在杭州"时：

```text
1. 保留原始事件 "我住在上海"
2. 记录纠正事件 "刚才开玩笑，我住在杭州"
3. 记忆分析 Agent 产生关系: supersedes / superseded_by
4. 旧记忆不删除，但被标记为被替代
5. 检索时默认返回最新有效版本
6. 审计时可见完整历史
```

### 4.6 关系状态

继续沿用当前的 `relationships(persona_id, actor_id)` 模型，但未来需要区分：

- 人格—参与者关系（跨空间）
- 参与者在特定空间中的行为侧面

关系状态可以影响称呼、语气和互动距离，但关系状态本身不应成为可向群成员披露的数据。

## 5. Layer 3: Social State — 社交状态层

### 5.1 核心洞察

ChatLuna Character 的 `status` 机制表明：

> 在短期记忆和长期记忆之间，需要一层"当前社交状态"。

这层状态的生命周期介于几秒到几天，负责控制下一步行动，而不是长期存储。

### 5.2 社交状态结构

```text
SocialState(space_id)
├── current_topic          当前话题
├── pending_questions[]    待回答的问题及提问者
├── waiting_for
│   ├── actor_id           在等谁
│   ├── expected_action    期望什么行动
│   └── deadline            截止时间
├── unfulfilled_promises[] 未完成的承诺
│   ├── promise             承诺内容
│   ├── to_actor            对谁承诺
│   └── by_when             何时之前
├── temporary_mood          临时情绪
├── recent_decisions[]     近期决定
├── active_threads[]        活跃的回复线程
└── version                 状态版本
```

### 5.3 与长期记忆的边界

| 维度     | Social State                | 长期记忆                    |
| -------- | --------------------------- | --------------------------- |
| 生命周期 | 秒到天                      | 周到年                      |
| 更新方式 | 每轮自动更新                | Agent 提取 + 衰减           |
| 存储位置 | 快速 KV / 内存 + 定期持久化 | SQLite + ChromaDB           |
| 检索方式 | 直接读取                    | 语义检索                    |
| 典型内容 | "正在等 A 回答数据库问题"   | "A 是后端工程师，主要用 Go" |

### 5.4 状态持久化

参考 ChatLuna Character 的 `statusPersistence`：

- 社交状态应持久化到数据库
- 插件重启后可以恢复
- 但不应替代长期记忆
- 状态过期后可以清理

## 6. Layer 4: Social Decision — 社交决策层

### 6.1 核心洞察

ChatLuna Character 最有价值的设计是：

> "何时发言"不应该是 Prompt 的一部分，而应该是显式的运行时机制。

### 6.2 决策流水线

**核心约束**：Mnemosync 对外是一个 OpenAI 兼容的模型服务商，调用方（平台适配器）是不可控的。任何要求平台适配器做特殊适配的方案都不可行。

#### 6.2.1 默认模式：平台触发，人格始终回复

```text
平台适配器                             Mnemosync
─────────                             ─────────
┌─────────────────┐
│ 1. 触发检测      │
│  @ / 关键词 /    │
│  间隔 / 活跃度   │
│  概率 / 定时     │
│                  │
│  是否发言由平台  │
│  插件生态决定    │
└────────┬────────┘
         │ 触发
         │ POST /v1/chat/completions
         ▼
         ┌─────────────────┐
         │ 2. 内容生成      │
         │  加载记忆与关系  │
         │  模型生成回复    │
         │  始终返回响应    │
         └────────┬────────┘
                  │ 回复
                  ▼
         ┌─────────────────┐
         │ 3. 动作执行      │
         │  发送、分段、    │
         │  模拟打字        │
         └─────────────────┘
```

这是前期默认行为。Mnemosync 只做"收到请求 → 加载记忆和关系 → 生成回复"。平台适配器全权负责何时触发——这正是 AstrBot 等框架的插件生态的优势所在，不需要 Mnemosync 复述或覆盖。

人格的"沉默"体现在回复内容本身——模型可以在 Prompt 引导下，对不想参与的话题给出简短回应，对想参与的话题给出充分回应。这不是"不说话"，而是"参与度的自然变化"。

#### 6.2.2 可选增强：被动沉默

用户可手动开启。当人格判断当前不应回复时，Mnemosync 直接**超时或返回空响应体**——这是 OpenAI 兼容接口本身允许的行为，不需要平台适配器做任何适配。平台收到超时或空响应自然就不会发送消息。

```text
平台适配器                             Mnemosync
─────────                             ─────────
POST /v1/chat/completions
         ──────────────────────────►
                                      ┌─────────────────┐
                                      │ 加载记忆与关系  │
                                      │ 人格判断：      │
                                      │ 此时不应回复    │
                                      └────────┬────────┘
                                               │
                                      ┌────────▼────────┐
                                      │ 返回超时        │
                                      │ 或空响应体      │
                                      └────────┬────────┘
         ◄──────────────────────────
平台收到超时/空响应
→ 自然不发送消息
→ 不需要任何特殊处理
```

**关键设计原则**：

- 超时和空响应体是 HTTP 和 OpenAI 协议的固有行为，**不是 Mnemosync 的自定义约定**
- 任何 OpenAI 兼容客户端都已经能处理这两种情况
- 不需要平台适配器识别 `[SILENT]` 标记、调用额外端点、或订阅任何事件
- 人格的"沉默"能力是 Mnemosync 的内部实现细节，对外不可见

**沉默的判断依据**（仅限可选增强模式）：

- 当前参与者与人格的关系状态（如信任度极低）
- 当前话题是否在人格的行为边界内
- 人格是否处于强制静默状态
- 是否触发了人格的禁言规则

默认模式下这些判断不生效，人格始终回复。可选增强模式由用户手动开启，用户承担回复频率降低的后果。

### 6.3 触发机制

| 触发类型 | 说明               | 负责层     |
| -------- | ------------------ | ---------- |
| @提及    | 被 @ 时触发        | 平台适配器 |
| 关键词   | 包含预设关键词     | 平台适配器 |
| 固定间隔 | 每 N 条消息触发    | 平台适配器 |
| 聚合等待 | 连续 N 秒无新消息  | 平台适配器 |
| 活跃度   | 群消息速率达到阈值 | 平台适配器 |
| 空闲触发 | 长时间无人发言     | 平台适配器 |
| 随机概率 | 按概率随机触发     | 平台适配器 |

所有触发机制由平台适配器全权负责。Mnemosync 不参与触发决策——它只响应到达的请求。

### 6.4 沉默决策

沉默不是 Mnemosync 的独立功能，而是**平台触发策略的自然结果**：

- 平台不触发 → Mnemosync 不收到请求 → 人格不发言
- 平台触发 → Mnemosync 收到请求 → 人格回复（默认模式）
- 平台触发 → Mnemosync 收到请求 → 人格判断可超时/空响应（可选增强模式，用户手动开启）

平台插件生态中已有的禁言词、冷却时间、白名单等机制继续正常工作，Mnemosync 不替代它们。

---

## 7. Layer 5: Response Content — 回复内容层

### 7.1 核心约束

Mnemosync 对外是一个 OpenAI 兼容的模型服务商。调用方（平台适配器）是不可控的黑盒，不知道 Mnemosync 的存在。因此：

> Mnemosync 只能返回普通文本。不能定义自己的结构化格式要求平台适配器解析。

### 7.2 回复内容的自然表达

人格的社交表达（引用、@、分段等）通过**自然语言和平台原生语法**实现，不需要 Mnemosync 定义特殊格式：

| 社交意图 | 实现方式 | 示例 |
|---------|---------|------|
| 引用某条消息 | 平台 system prompt 中已有的引用格式要求 | 按平台要求的格式引用 |
| @ 某人 | 平台 system prompt 中已有的 @ 语法 | 按平台要求的格式 @ |
| 分段发送 | 返回多条消息 | 平台自行决定发送方式 |
| 发送表情 | 平台 system prompt 中已有的表情语法 | 按平台要求的格式插入表情 |

### 7.3 与平台适配器的分工

**Mnemosync 负责**：

- 在人格 Prompt 中引导模型使用平台 system prompt 要求的回复格式
- 按前台要求的格式返回内容
- 如果前台没有要求任何特殊格式，返回普通文本

**平台适配器（不可控）负责**：

- 在 system prompt 中定义自己支持的格式（引用语法、@ 语法、分段规则等）
- 解析模型返回的文本并执行平台发送动作
- 分条发送、模拟打字等

### 7.4 如果前台要求了结构化输出

如果平台适配器在 system prompt 中已经要求了 JSON 或特定格式，Mnemosync 可以遵从该格式生成回复。但这取决于平台适配器的要求，不是 Mnemosync 自己定义的协议。

```text
平台发送的 system prompt 包含：
  "回复格式：{ "reply": "文本内容", "quote": "引用的消息ID" }"

↓

Mnemosync 人格遵从该格式生成回复

↓

平台适配器按自己定义的格式解析并执行
```

Mnemosync 不创造格式，只遵从格式。

## 8. Layer 6: Platform Adapter — 平台适配层

### 8.1 职责

平台适配器完全在 Mnemosync 核心之外，负责：

```text
┌─────────────────────────────────────────┐
│           Platform Adapter               │
│                                           │
│  输入方向                                 │
│  • 接收平台事件（消息、撤回、入群等）     │
│  • 消息聚合和防抖                        │
│  • 身份断言（提供可信身份元数据）         │
│  • 媒体预处理（OCR、STT、图片压缩）       │
│  • 触发条件检测                          │
│                                           │
│  输出方向                                 │
│  • 执行发送动作（文本、图片、语音等）     │
│  • 分段发送和模拟打字                    │
│  • 表情包/Sticker 发送                   │
│  • 平台特有元素渲染                      │
│  • 撤回和编辑                            │
│                                           │
│  状态管理                                 │
│  • 群成员列表缓存                        │
│  • 消息 ID 映射                          │
│  • 发送队列和冷却                        │
│  • 连接状态                              │
└─────────────────────────────────────────┘
```

### 8.2 身份断言

平台适配器向 Mnemosync 提供的身份信息：

```text
integration_id      哪个适配器实例
platform            qq / telegram / discord / web
external_actor_id   平台侧用户标识
external_space_id   平台侧群/私聊标识
channel_type        group / direct
external_event_id   平台侧消息 ID（用于幂等）
reply_to_event_id   被回复的消息（可选）
provider_timestamp  平台事件时间（可选）
```

Mnemosync 将这些映射为内部的 `actor_id`、`space_id` 和 `event_id`。

### 8.3 无可信身份时

如果请求只有一句用户文本，没有可信用户或群标识：

- 不创建或更新具体用户关系
- 不写入已有用户私有记忆
- 不检索任何具体用户私有记忆
- 按当前 v0.2.x 单用户模式处理
- 调试界面应明确标示"身份未归属"

## 9. 辅助 Agent 架构

### 9.1 核心洞察

ChatLuna 子代理系统和 Hermes Memory Provider 的共同启示：

> 辅助 Agent 应该共享统一的运行契约，而不是每个 Agent 各自实现。

### 9.2 统一的 Agent 规范

```text
AgentSpec
├── name                   名称
├── purpose                用途描述
├── input_schema           输入 Schema
├── output_schema          输出 Schema
├── model                  使用模型
├── prompt_version         提示词版本
├── allowed_tools[]        允许的工具
├── timeout                超时
├── max_iterations         最大迭代次数
├── concurrency_policy     并发策略
├── persistence_policy     持久化策略
└── privacy_scope          隐私范围
```

### 9.3 统一的运行记录

```text
AgentRun
├── run_id                 运行 ID
├── parent_request_id      父请求 ID
├── agent_name              Agent 名称
├── input_event_ids[]      输入事件
├── base_version           基础版本
├── started_at / finished_at
├── status                 running / completed / failed / aborted
├── tool_trace[]           工具调用轨迹
├── usage                   Token 用量
├── structured_result      结构化结果
└── error                  错误信息
```

### 9.4 未来的辅助 Agent 职责

| Agent            | 输入                       | 输出                         | 安全边界                       |
| ---------------- | -------------------------- | ---------------------------- | ------------------------------ |
| **身份归一化**   | 受信任集成元数据           | actor_id / space_id          | 确定性代码为主，LLM 不决定身份 |
| **空间摘要**     | 一段空间公共事件           | 结构化检查点                 | 不得读取用户私聊记忆           |
| **记忆分析**     | 当前事件及允许的关联上下文 | 带主体、受众、来源的候选记忆 | 不得自行扩大受众               |
| **关系分析**     | 当前参与者与人格的互动     | 版本化关系更新建议           | 必须绑定 actor_id              |
| **隐私策略检查** | 候选上下文 / 候选回复      | 允许、拒绝或降级             | 确定性策略优先                 |
| **冲突合并**     | 同主体、同受众的相关记忆   | 合并或冲突建议               | 保留来源和人工审计             |

### 9.5 运行模式

参考 ChatLuna 子代理：

```text
同步模式
  父流程调用 Agent → 等待结果 → 继续

后台模式
  父流程启动 Agent → 立即继续 → Agent 完成后通知

并行模式
  多个独立 Agent 同时运行
```

所有异步结果必须携带输入事件版本，提交时若基础版本已变化应重新验证。

## 12. 必须保持的架构不变量

无论演进到哪个阶段：

1. **单人格不变量**：一个实例 = 一个人格 = 服务器权威
2. **身份不变量**：API Key 证明前端，不证明用户；身份来自受信任断言
3. **隐私不变量**：先按受众过滤，再把记忆交给模型；绝不能反过来
4. **客户端不变量**：核心功能不依赖客户端修改
5. **来源不变量**：记忆必须携带来源和提取上下文
6. **人格权威不变量**：客户端 system 消息不被信任为人格定义

## 15. 结论

Mnemosync 的未来架构应该是一个六层模型：

```text
Persona Definition  →  人格是谁、怎样表达
Memory & Relationship → 人格记得什么、与谁什么关系
Social State        →  当前在做什么、在等谁
Social Decision     →  可选被动沉默（超时/空响应）
Response Content    →  遵从平台格式的文本回复
Platform Adapter    →  平台事件、触发决策与发送
```

前三层属于 Mnemosync 核心，后三层属于平台适配器。Layer 4 的被动沉默是 Mnemosync 内部可选功能，不依赖平台配合。

角色卡让人格可以被携带，Lorebook 让静态知识可以按需注入，长期记忆让动态事实可以跨会话持续，社交状态让人格知道当前在做什么，人格 Prompt 引导模型在回复中自然表达其社交风格。

**当这六层完整时，Mnemosync 就不再只是一个"带记忆的问答接口"，而是一个真正持续存在、可以出门社交的人格。**
