# 单人格多用户群聊架构预留（AstrBot / QQ 群） | Single-Persona Multi-User Group Chat Design Reservation

> **文档版本**: v0.3.0-draft
> **创建时间**: 2026-07-24
> **最后更新**: 2026-07-24
> **状态**: 设计预留 · 未进入开发 (Design Reservation · No Implementation)
> **基准场景**: Mnemosync → AstrBot（或其他 ChatBot / Agent 框架）→ QQ 机器人 → QQ 群

---

## 1. 文档目的与边界

本文为未来“**一个服务器权威人格同时与多个用户交往**”预留架构边界，不代表当前版本承诺，也不要求修改现有代码、数据库或客户端。

当前 v0.2.x 仍维持既定设计：

- 一个 Mnemosync 实例对应一个人格；
- 多个接入前端代表同一个用户；
- `source_user='default'`、`persona_id='default'` 是当前阶段的设计，不是缺陷；
- 服务端持有对话和人格真相，不信任客户端自行定义人格；
- 当前功能不依赖不可控的 OpenAI 兼容客户端配合修改。

本文只回答未来设计问题：

1. 同一个人格进入群聊后，如何识别参与者和会话空间；
2. 如何同时维护人格核心、群公共上下文、个人关系和个人记忆；
3. 如何处理并发、异步、乱序、重复消息；
4. 如何避免跨用户、跨群和跨受众泄露记忆；
5. Pi Agent 的树形会话设计可提供哪些启发，又有哪些部分不能直接照搬。

### 1.1 非目标

本文不决定：

- 具体数据库表和迁移 SQL；
- AstrBot 插件或适配器实现；
- 队列、中间件和分布式锁选型；
- QQ 平台 SDK 选型；
- 多人格或人格复制；
- 管理员查看用户私密记忆的权限；
- 具体版本排期。

## 2. 为什么以群聊作为基准场景

群聊天然包含普通多用户私聊没有同时暴露的约束：

```text
QQ 群 G
├── 用户 A：连续发出两条相关消息
├── 用户 B：插入一句追问
├── 用户 C：回复 A 较早的一条消息
├── 用户 D：只旁观，不直接呼叫机器人
└── 人格：可能同时收到多个待回复事件
```

它覆盖：

- 多用户身份；
- 同一公共空间中的交叉对话；
- 不同用户之间的关系和隐私边界；
- 回复引用、@、话题切换；
- 消息重复、乱序和并发；
- 群内公共经验与个人私密经验并存；
- 人格在不同群、私聊、前端之间切换。

如果群聊架构成立，私聊可以视为只有人格和一个用户参与、受众更小的会话空间。私聊在上下文拓扑上更简单，但跨平台身份关联、同意和隐私仍需单独设计。

## 3. 核心术语

| 术语                              | 含义                                                                     |
| --------------------------------- | ------------------------------------------------------------------------ |
| **人格 (Persona)**                | 服务器端权威定义的单一人格，包括核心身份、行为边界和人格公共记忆         |
| **参与者 (Actor)**                | 与人格交互的真实用户；平台账号只是参与者的一种外部身份                   |
| **前端来源 (Source Frontend)**    | AstrBot、AIRI、Web 等接入应用，由 API Key 等服务端凭据识别               |
| **会话空间 (Conversation Space)** | 消息被共同感知的范围，例如 QQ 群、QQ 私聊、Web 会话                      |
| **消息事件 (Message Event)**      | 某个参与者在某个空间发出的一次不可变输入，带来源、时间、回复关系等元数据 |
| **主体 (Subject)**                | 一条记忆“关于谁或什么”，例如人格、用户 A、群 G 或某个话题                |
| **受众 (Audience)**               | 一条信息“允许被谁知道或在哪个空间使用”                                   |
| **关系状态 (Relationship State)** | 人格与某个参与者之间独立维护的亲密、信任、称呼和互动状态                 |
| **空间上下文 (Space Context)**    | 一个群或私聊空间内的最近事件、摘要、公共约定和活跃话题                   |
| **检查点 (Checkpoint)**           | 旧事件的结构化摘要及必要状态，用于控制上下文长度；不替代原始事件         |
| **幂等 (Idempotent)**             | 同一个消息事件被重复提交时，只产生一次有效处理结果                       |

### 3.1 主体与受众必须分离

“记忆关于谁”与“谁可以获知这条记忆”不是同一维度。

例如：

```text
内容：用户 A 对花生过敏
主体：用户 A
受众：仅人格与用户 A 的私聊
```

这条记忆即使“关于用户 A”，也不代表可以在用户 A 所在的任何群里公开提及。

## 4. 目标模型：人格、参与者与空间

未来模型不是把不同用户简单视为同一棵树上的分支，而是三个正交维度：

```text
                         ┌─────────────────────┐
                         │  单一人格 Persona P │
                         │  核心身份 / 公共记忆 │
                         └─────────┬───────────┘
                                   │
             ┌─────────────────────┼─────────────────────┐
             │                     │                     │
      ┌──────▼──────┐       ┌──────▼──────┐       ┌──────▼──────┐
      │ 参与者 A     │       │ 参与者 B     │       │ 参与者 C     │
      │ 关系 / 私有记忆│       │ 关系 / 私有记忆│       │ 关系 / 私有记忆│
      └──────┬──────┘       └──────┬──────┘       └──────┬──────┘
             │                     │                     │
             └──────────┬──────────┴──────────┬──────────┘
                        │                     │
                 ┌──────▼──────┐       ┌──────▼──────┐
                 │ QQ 群空间 G1 │       │ QQ 群空间 G2 │
                 │ 公共事件/摘要 │       │ 公共事件/摘要 │
                 └─────────────┘       └─────────────┘
```

同一个参与者可能存在于多个空间；同一个空间有多个参与者；同一个人格服务多个空间。

因此未来主键和隔离边界不能只依赖一个 `source_user`，至少需要逻辑上的：

```text
persona_id      人格
actor_id        参与者
space_id        会话空间
source_frontend 接入来源
external_id     平台侧账号或群标识
```

具体字段、表结构和命名留待实现阶段决定。

## 5. 必须保持的架构不变量

### 5.1 单人格不变量

- 一个实例仍只有一个服务器权威人格；
- 用户不能通过请求中的 system 消息替换或重定义人格；
- 多用户只增加关系和记忆分区，不创建多个人格副本；
- 人格公共身份应跨空间一致。

### 5.2 身份不变量

- API Key 只证明“哪个前端在调用”，默认不证明“当前用户是谁”；
- `actor_id` 必须来自受信任的集成身份断言，不能从自然语言内容、昵称或客户端 system prompt 猜测；
- 同一个平台账号是否与另一个平台账号属于同一真人，未经显式绑定不得自动合并；
- 无法获得可信参与者身份时，必须进入“未归属模式”，不得把内容写入任何已有用户的私有记忆。

### 5.3 隐私不变量

- 先按受众过滤，再把记忆交给模型；不能先注入私密记忆，再仅靠提示词要求模型不要泄露；
- 其他用户的私有记忆永远不进入当前群聊请求的模型上下文；
- 当前用户的私聊记忆默认也不进入群聊上下文；
- 群内公开说过的话可以成为群历史，但不应自动升级为跨群公共记忆；
- 原始消息、提取记忆、关系状态和可输出信息应分别管理。

### 5.4 并发与一致性不变量

- 原始消息事件追加保存，不因压缩、撤回视图或摘要生成而覆盖；
- 同一外部消息重复到达时不得重复回复、重复计数或重复写记忆；
- 同一空间需要明确的服务端提交顺序；不同空间可以并行；
- 后台分析结果必须关联输入事件和状态版本，过期结果不能覆盖更新状态；
- 不假设全局只有一个“活动叶节点”或一个正在对话的用户。

### 5.5 客户端边界不变量

Mnemosync 核心不能要求所有通用 OpenAI 兼容客户端为多用户功能改变行为。

未来多用户模式只能在集成层已经能提供可信身份和空间信息时启用，例如：

- 框架原生提供的标准字段；
- Mnemosync 官方支持的服务端适配器；
- 经过认证的网关身份断言。

如果集成层不提供这些信息，Mnemosync 应明确降级为当前单用户模式或未归属公共模式，而不是假装已正确区分用户。

## 6. Pi Agent 树结构带来的启发

Pi Agent 的会话树主要解决同一个任务中“回到过去节点并走另一条路线”的问题。它不是多用户访问控制系统，但以下设计值得借鉴。

### 6.1 可借鉴部分

#### 追加式类型化事件

Pi 不只保存聊天文本，还保存消息、模型切换、压缩、分支摘要和扩展状态。群聊也应把输入视为带类型和来源的事件，而不是把所有人的文字拼成一个字符串。

#### 存储与上下文投影分离

完整事件长期保存；每次模型调用只投影当前空间、当前受众和当前任务需要的部分。

#### 检查点而非删除

上下文过长时生成“空间摘要 + 最近事件”，原始历史仍保留用于审计、重新摘要和纠错。

#### 类型化辅助任务输出

群摘要 Agent、记忆分析 Agent、关系分析 Agent 应返回结构化结果，并携带输入事件范围和版本，而不是直接修改主消息列表。

### 6.2 不能直接照搬部分

| Pi 设计                   | 群聊中不能直接照搬的原因                   |
| ------------------------- | ------------------------------------------ |
| 一个活动叶节点            | 多个群和用户可同时活跃                     |
| 用户主动选择分支          | 群消息由多个人异步产生，不是一个人选择路线 |
| 分支共享全部祖先          | 不同用户之间存在隐私和受众边界             |
| Branch Summary 跨分支迁移 | 不能把一个用户的经验自动迁移给其他用户或群 |
| 单棵 Session Tree         | 不能承担身份认证、授权和跨空间隔离         |

### 6.3 更合适的抽象

群聊更接近：

```text
每个会话空间一条有序事件流
+ 回复/引用形成的局部关联图
+ 每个参与者独立的关系和私有记忆
+ 人格层的公共核心
+ 从事件流生成的可重建检查点
```

它可以借鉴 Pi 的事件、投影和检查点机制，但不应把“用户”建模成会话树的分支。

## 7. 身份与集成边界

### 7.1 身份断言

受信任的集成层至少需要表达：

```text
integration_id      哪个 AstrBot / Agent 框架实例
platform            qq / telegram / discord / web / ...
external_actor_id   平台侧用户标识
external_space_id   平台侧群或私聊标识
channel_type        group / direct
external_event_id   平台侧消息 ID
reply_to_event_id   被回复的消息（可选）
provider_timestamp  平台事件时间（可选）
```

Mnemosync 将这些外部标识映射为内部 `actor_id`、`space_id` 和 `event_id`。原始平台 ID 不应直接承担跨平台身份合并。

### 7.2 信任来源

推荐信任顺序：

1. 经过认证的官方适配器或网关断言；
2. 与 API Key / 集成实例绑定并经过校验的标准请求字段；
3. 未验证字段只能作为显示元数据，不能作为私有记忆分区主键；
4. 从消息正文或昵称推断身份仅用于展示，不用于授权。

### 7.3 无可信身份时的降级

如果请求只有一句用户文本，没有可信用户或群标识：

- 不创建或更新具体用户关系；
- 不写入已有用户私有记忆；
- 不检索任何具体用户私有记忆；
- 可以按当前 v0.2.x 模式处理，或作为未归属公共事件处理；
- 调试和管理界面应明确标示“身份未归属”。

## 8. 事件与并发模型

### 8.1 消息事件的概念字段

```text
MessageEvent
├── event_id              服务端唯一 ID
├── external_event_id     平台消息 ID，用于幂等
├── persona_id
├── actor_id
├── space_id
├── source_frontend
├── channel_type          group / direct
├── content
├── reply_to_event_id     回复关系，可空
├── provider_timestamp    平台声称的时间
├── received_at           服务端接收时间
├── committed_sequence    服务端在空间内分配的顺序
└── visibility            事件受众
```

以上是概念模型，不承诺具体表结构。

### 8.2 有序提交

建议初始一致性语义：

- 同一 `space_id` 使用单写入者或等价的有序提交机制；
- 不同 `space_id` 可以并行；
- `provider_timestamp` 用于展示和诊断，不单独决定提交顺序；
- 到达较晚的旧消息不应按任意固定阈值自动丢弃；应保留事件并标记迟到，根据回复关系和平台序列决定是否参与当前上下文；
- 回复生成要记录它基于哪个空间版本构建，以便检测响应完成前空间是否已发生显著变化。

### 8.3 幂等与重试

同一个 `(integration_id, external_event_id)` 重复提交时：

- 只产生一个消息事件；
- 只生成一次有效回复；
- 关系互动次数只增加一次；
- 记忆分析只提交一次有效结果；
- 重试可以返回已有处理状态或结果。

### 8.4 是否必须串行回复

本文不预先决定同一群必须完全串行。候选语义包括：

- **严格串行**：一致性最强，延迟随队列增长；
- **并行生成、顺序提交**：降低模型等待，但需检测上下文版本冲突；
- **按回复线程并行**：依赖平台可靠提供 reply-to 信息；
- **快照隔离**：每个请求读取空间快照，回复携带其依据版本。

实现前应先确定产品期望，而不是直接选择锁或队列技术。

## 9. 记忆的主体与受众模型

### 9.1 建议的记忆类别

| 类别                         | 主体           | 典型受众                    | 示例                                           |
| ---------------------------- | -------------- | --------------------------- | ---------------------------------------------- |
| **人格核心记忆**             | Persona        | 所有空间                    | 人格身份、稳定价值观、公开能力边界             |
| **参与者私有记忆**           | Actor          | 人格内部 + 与该参与者的私聊 | 用户 A 的个人偏好、健康信息                    |
| **空间公共记忆**             | Space          | 该空间参与者                | 群规、群内共同项目、已公开的群约定             |
| **参与者在空间内共享的记忆** | Actor + Space  | 指定空间                    | 用户 A 在群 G 主动公开的称呼偏好               |
| **临时会话状态**             | Space / Thread | 当前上下文窗口              | 当前话题、待回答问题、短期指代                 |
| **人格内部经验**             | Persona        | 仅人格内部                  | 从互动中总结的方法，但不得包含可识别的用户隐私 |

### 9.2 群聊检索规则

对群聊输出，默认可检索：

- 人格核心中允许公开的部分；
- 当前群的空间公共记忆；
- 当前用户明确允许在该群共享的记忆；
- 当前群最近的可见事件和检查点；
- 关系状态导出的行为提示，例如称呼和语气，但不注入其私密来源事实。

默认不可检索：

- 其他用户的私有记忆；
- 当前用户只允许私聊使用的记忆；
- 其他群的空间记忆；
- 未经策略批准的跨群或跨用户推断；
- 仅凭模型判断可能有用、但受众不匹配的内容。

### 9.3 私聊检索规则

私聊可以额外检索当前参与者的私有记忆，但仍不能检索其他用户的私有记忆。群里公开过的信息是否进入该用户私聊，应由记忆受众和来源策略决定，不能仅因内容存在于数据库就自动加载。

### 9.4 记忆提升与迁移

从局部空间向更广受众提升必须保守：

```text
临时事件 → 空间记忆 → 人格内部通用经验 → 人格公共记忆
```

提升不是自动复制。每一步都要检查：

- 是否含可识别个人信息；
- 原始发言的受众和语境；
- 用户是否明确公开；
- 能否去标识化；
- 是否真的是通用经验；
- 是否存在撤回、纠正或冲突。

## 10. 关系模型

### 10.1 人格—参与者关系

每个参与者与人格拥有独立关系状态：

```text
Relationship(persona_id, actor_id)
├── relationship_type
├── intimacy_score
├── trust_level
├── interaction_count
├── addressing
├── last_active
└── version
```

当前 `relationships(persona_id, user_id)` 已为这一方向保留概念基础，但未来应先明确 `user_id` 与平台身份、内部参与者身份之间的映射。

### 10.2 空间状态不是用户关系

群不是普通用户。人格对群的熟悉程度、群风格和群约定应作为 `Space State` 管理，不建议仅通过伪造 `user_id=group_id` 塞进用户关系表。两者生命周期和权限不同。

### 10.3 关系状态的使用

关系状态可以影响：

- 称呼；
- 语气和互动距离；
- 是否主动接续旧话题；
- 对不确定推断的谨慎程度。

关系状态本身不应成为可向群成员披露的数据。例如不应回复“我对用户 B 的信任度是 0.2”。

## 11. 群聊上下文组装

### 11.1 分层装填

```text
1. 请求身份与受众
   ├── 当前人格
   ├── 当前参与者
   ├── 当前会话空间
   └── 输出受众（群 / 私聊）

2. 人格核心
   ├── 服务器权威 system prompt
   └── 当前受众允许使用的人格核心记忆

3. 空间上下文
   ├── 空间规则和公共记忆
   ├── 空间检查点 / 摘要
   └── 最近可见事件（带说话者标签和回复关系）

4. 当前参与者上下文
   ├── 关系导出的称呼和语气提示
   └── 仅加载当前受众允许的参与者记忆

5. 当前消息
   ├── 内容
   ├── 回复目标
   └── @ / 提及信息
```

### 11.2 群聊不是“每个用户一条独立短期历史”

如果只加载当前用户的历史，模型会看不到群中其他人刚刚说了什么；如果把所有人的全部历史都加载，又会产生隐私和 token 问题。

因此短期上下文应以**空间事件流**为主，个人历史和关系作为受众受控的补充：

```text
群最近事件（公共）
+ 当前用户在本群的相关公开历史
+ 当前用户关系提示
+ 当前消息
```

### 11.3 检查点

群事件过长时，可以借鉴 Pi 的 Compaction：

- 保存原始事件；
- 生成结构化空间摘要；
- 保留最近事件尾部；
- 摘要记录覆盖的事件范围、生成模型、提示词版本和输入空间版本；
- 后续可从原始事件重新生成；
- 空间摘要不得吸收用户私聊记忆。

建议空间摘要至少保留：

```text
当前话题
已确认的群内公开事实
未回答问题及提问者
近期决定
回复关系或争议点
摘要覆盖的事件范围
```

## 12. 辅助 Agent 的未来职责

以下只是职责划分，不代表必须为每项创建独立模型调用。

| 职责             | 输入                       | 输出                         | 安全边界                              |
| ---------------- | -------------------------- | ---------------------------- | ------------------------------------- |
| **身份归一化**   | 受信任集成元数据           | actor_id / space_id          | 应以确定性代码为主，不让 LLM 决定身份 |
| **空间摘要**     | 一段空间公共事件           | 结构化检查点                 | 不得读取用户私聊记忆                  |
| **记忆分析**     | 当前事件及允许的关联上下文 | 带主体、受众、来源的候选记忆 | 不得自行扩大受众                      |
| **关系分析**     | 当前参与者与人格的互动     | 版本化关系更新建议           | 必须绑定 actor_id，禁止跨用户修改     |
| **隐私策略检查** | 候选上下文 / 候选回复      | 允许、拒绝或降级             | 确定性策略优先，模型只能辅助          |
| **冲突合并**     | 同主体、同受众的相关记忆   | 合并或冲突建议               | 保留来源和人工可审计性                |

所有异步结果均应包含：

```text
input_event_ids
persona_id
actor_id（如适用）
space_id（如适用）
base_version
result_type
provenance
```

提交时若基础版本已经变化，应重新验证或放弃，而不是覆盖新状态。

## 13. 典型安全与正确性场景

### 13.1 私聊秘密不得在群里泄露

```text
私聊：A 告诉人格“我准备辞职，先别告诉别人”
群聊：B 问“最近 A 有什么计划？”
期望：A 的私密记忆没有进入这次群聊模型上下文。
```

### 13.2 同一昵称不是同一用户

```text
群 G1 有昵称“小明”的账号 X
群 G2 有昵称“小明”的账号 Y
期望：不根据昵称合并身份和记忆。
```

### 13.3 跨平台账号不自动合并

```text
QQ 账号 X 和 Web 账号 Y 都自称 A
期望：未经绑定，不共享私有记忆和关系状态。
```

### 13.4 重复投递

```text
AstrBot 因超时重试，同一 external_event_id 到达两次
期望：只生成一次有效回复，只写一次记忆，只增加一次互动计数。
```

### 13.5 并发更新关系

```text
A 在两个空间几乎同时与人格互动
期望：两个关系分析结果不会互相覆盖；旧版本更新被拒绝或重新合并。
```

### 13.6 群内公开不等于全局公开

```text
A 在群 G1 公开自己的职业
A 也在群 G2
期望：除非策略允许，不在 G2 主动引用 G1 的内容。
```

### 13.7 无身份信息的请求

```text
某 OpenAI 兼容客户端只传 messages，没有用户或空间元数据
期望：系统不把这条消息错误归入任一已有用户，不启用多用户私有记忆。
```

### 13.8 撤回与纠正

```text
A 公开说“我住在上海”，随后纠正“刚才开玩笑，我住在杭州”
期望：保留原始事件和纠正来源；记忆分析产生冲突/更新，而不是两个事实同时生效。
```

## 14. 概念上的数据域

未来可以按职责划分以下数据域，具体是否分表、分库或分服务留待实现阶段决定：

```text
Identity Domain
├── Integration
├── ExternalIdentity
├── Actor
└── IdentityLink / Consent

Conversation Domain
├── Space
├── Membership
├── MessageEvent
├── ReplyEdge
└── Checkpoint

Memory Domain
├── MemoryEntry
├── SubjectScope
├── AudienceScope
├── Provenance
└── Conflict / Supersession

Relationship Domain
├── PersonaActorRelationship
├── RelationshipAudit
└── SpaceState
```

现有字段可作为迁移起点：

- `memory_entries.source_user`；
- `relationships.persona_id`；
- `relationships.user_id`；
- `conversation_turns.source_frontend`。

但不能仅将 `source_user` 从 `default` 改成 QQ 号就认为多用户设计完成；身份可信度、空间、受众、幂等和并发仍然缺失。

## 15. 分阶段研究路线（非开发计划）

### 阶段 A：契约研究

- 调查 AstrBot 当前请求中实际可用的用户、群、消息和回复元数据；
- 明确哪些信息无需修改客户端即可取得；
- 定义可信身份断言和降级模式；
- 收集 QQ 群的重复、乱序、撤回、回复和 @ 行为样本。

### 阶段 B：领域设计

- 确定 Actor、Space、Event、Memory Subject、Audience 的类型；
- 确定跨平台身份绑定是否存在以及如何征得同意；
- 确定群公开、群内用户共享、私聊私有等受众规则；
- 确定人格核心与人格内部经验的边界。

### 阶段 C：一致性设计

- 确定空间内的处理和提交顺序；
- 确定幂等键、版本控制和后台结果提交规则；
- 确定严格串行、并行生成或快照隔离的产品语义；
- 确定消息撤回和纠正如何影响摘要与记忆。

### 阶段 D：验证设计

- 用合成事件而非浏览器模拟验证并发、乱序和隔离；
- 建立隐私泄露测试矩阵；
- 验证跨群、跨用户、跨前端不会错误召回；
- 验证无身份元数据时安全降级。

## 16. 开放问题

1. AstrBot 现有 OpenAI 兼容调用是否稳定携带用户、群、消息 ID 和回复关系？
2. QQ 号是否可以直接作为内部身份，还是必须做平台命名空间和不可逆映射？
3. 同一参与者跨群时，哪些关系状态共享，哪些按空间分层？
4. 群内公开记忆是否允许在同一用户私聊中使用？反方向默认应禁止。
5. 用户如何查看、纠正、删除或限制人格关于其本人的记忆？
6. 群管理员是否有任何记忆治理权限？其权限能否覆盖个人隐私？
7. 人格从多个用户处学到的通用经验如何去标识化并进入人格内部经验？
8. 空间摘要由主模型、辅助模型还是确定性规则生成？
9. 机器人被移出群后，群空间数据的保留和删除策略是什么？
10. 多群高并发时，一致性边界应在单进程、数据库还是消息队列层实现？
11. 私聊与群聊是否共享同一个人格—参与者关系，还是维护渠道维度的关系侧面？
12. 当前 `PERMANENT` 记忆中哪些属于人格核心，哪些其实属于当前单用户，迁移时如何区分？

## 17. 结论

QQ 群聊适合作为未来单人格多用户架构的压力场景，因为它同时暴露身份、空间、受众、并发和记忆隔离问题。

Pi Agent 的主要启发不是“把每个用户放进会话树的一个分支”，而是：

- 使用追加式、类型化事件保存完整历史；
- 将持久存储与模型上下文投影分离；
- 通过检查点控制上下文长度，而不删除原始历史；
- 让辅助任务输出版本化、可审计的结构化结果。

未来 Mnemosync 更适合采用：

```text
单一服务器权威人格
+ 多参与者身份
+ 多会话空间事件流
+ 主体与受众分离的记忆
+ 每个参与者独立关系
+ 受众过滤后的上下文投影
```

在以上身份和隐私边界明确之前，不应仅通过解除 `source_user='default'` 硬编码来宣称支持多用户。
